# Hephaestus code notes

## Shared engine library migration

- `CMakeLists.txt:HephaestusGame` — `LUA_AVAILABLE` follows `LUA_FOUND` for every target, so `LuaScriptEngine.h` compiles the same way in the editor, the game and the shared runtime library. `HEPHAESTUS_GAME_SCRIPTING` only controls whether `engine/Game/GameMain.cpp:main` starts the Lua engine; when it is OFF the game still links Lua and ships its DLL (the package stager already requires `lua54.dll`).
- `engine/Gfx/EngineFrameRenderer.cpp:EngineFrameRenderer::recordBillboards` — light billboard icons (and their ID-buffer pass) are derived from `LightComponent::type` at draw time. The former `EditorIconComponent` was attached by a `Scene` constructor hook compiled only outside `HEPHAESTUS_GAME_RUNTIME`, which made `Scene` behave differently per host; it was never serialized, so removing it changes no saved data.
- `engine/Gfx/EngineFrameRenderer.h:EngineFrameRenderer::Init` — `editorOverlays` replaces the former `HEPHAESTUS_GAME_RUNTIME` compile-time branches, which changed the class layout per host (an ODR hazard once one library serves both). The editor (`QtEditorEngine`) passes `true`; `GameMain` passes `false`, so grid, debug overlay, outlines, ID picker, gizmos and billboards are never created in packaged games. Every `record*`/`cleanup*` path checks its own `initialized` flag, and `recordGrid` now checks `m_editorGrid.initialized` as well.
- `CMakeLists.txt:HephaestusRuntime` — the Qt-free engine as one static library with PUBLIC includes, links and `LUA_AVAILABLE`. `HephaestusGame` keeps only `GameMain.cpp`/`RuntimeBootstrap.cpp` and links it. Editor services (`EditorContext`, `PlayModeManager`, `EditorAssetPipeline`, `ReimportManager`, `FileWatcher`, `RecoveryStore`, `OpenDocumentRegistry`, `AssetOperationService`, `DerivedDataCache`, `EditorViewState`, `EditorCameraController`) were dropped from the game: nothing in the runtime includes them, and the game still links. Never add Qt to this target.
- `CMakeLists.txt:HephaestusPluginCore` — owns `engine/Assets/AssetPathPolicy.cpp` and `AssetReferenceIndex.cpp` next to `AssetMountRegistry.cpp`. They were compiled in both `HephaestusBuildCore` and the game; one owner avoids duplicate definitions once the editor links the runtime library and `BuildCore` together.
- `CMakeLists.txt:HephaestusEditorCore` — Qt-free editor services and documents (`EditorContext`, `PlayModeManager`, asset pipeline/reimport/recovery, `EditorDocument`, `MaterialEditor/*`, inspector selection and clipboard). Links `HephaestusRuntime` PUBLIC. `HephaestusEngine` now compiles only `engine/Core/main.cpp` plus the Qt sources and gets the engine, Lua, Vulkan, Jolt and include paths through this library. The unused `EDITOR_ONLY_SOURCES` list was removed.
- `CMakeLists.txt` test targets — 35 test executables link `HephaestusRuntime` (or `HephaestusEditorCore` when they cover editor services) instead of recompiling engine sources, so tests exercise the same objects and `LUA_AVAILABLE` value the hosts ship. Some tests that previously compiled `LuaScriptEngine` without `LUA_AVAILABLE` (the stub) now run against real Lua.
- `engine/Gfx/EngineFrameRenderer.cpp:EngineFrameRenderer::AddStaticMesh` — the one static-mesh upload, used by `GameMain` and `QtEditorEngine::uploadMeshToGPU`. It keeps the game's device-local staged upload (the editor previously used host-visible buffers; no code maps static mesh buffers after upload). `GameMain` registers the raw scene `meshAssetPath` as an alias because `sourceKey` is now `sourcePath.generic_string()`.
- `engine/Scripting/ScriptPhysicsBindings.cpp:MakeScriptPhysicsBinding` / `MakeScriptCharacterBinding` — the one implementation of the Lua `Physics.*` and `Character.*` callbacks, formerly copied in `GameMain.cpp` and `QtEditorEngine::StartPlayMode`. Hosts pass a `ScriptPhysicsAccessor` that is called on every script call: `GameMain` returns its fixed scene and systems; the editor returns null physics members unless `m_physicsInitialized` is set, so a physics restart in Play never leaves scripts holding stale pointers. Covered by `engine/Tests/PhysicsLuaTests.cpp`.
- `engine/Core/SimulationStep.cpp:RunSimulationStep` — the one gameplay frame order for Editor Play (realtime and `StepFrames`) and `GameMain`: audio sources, `PrepareSceneBodies`, C++ `UpdateScripts`, Lua `Update`, safe point, physics `Update` + contact dispatch, safe point, `CharacterAnimationSystem::Tick`, animation-finished + Lua `LateUpdate`, safe point, C++ `LateUpdateScripts`, safe point. `reloadAtSafePoint` processes a pending reload and ends the frame (returns `false`). `onPhysicsError` keeps the editor's existing behaviour (log, set `m_physicsInitialized = false`, skip physics for the rest of the frame); the game leaves it unset so physics exceptions still propagate. See the physics exceptions note under FPS blocker fixes. `PlayModeManager::Tick`/`StepTick` (no callers) and `BeginScriptFrame`/`FinishScriptFrame` were replaced by `PlayModeManager::AdvanceFrameTime`. Covered by `engine/Tests/SimulationStepTests.cpp`.
- `engine/Game/GameMain.cpp:main` — the packaged game now owns a C++ `ScriptEngine` (initialized after scene load, `AwakeScripts` at start and after a scene reload, `DestroyScripts` before reload, `Shutdown` at exit) and passes it to `RunSimulationStep`, matching Editor Play. Nothing attaches C++ scripts in packaged builds yet, so this has no visible effect until C++ scripting gains an attachment path.
- `engine/Gfx/BuiltinMeshes.cpp:AddBuiltinMeshes` — the one generator for `builtin://cube` (1x1x1), `builtin://plane`, `builtin://sphere` (radius 0.5) and `builtin://skinned_rest_fixture`, used by `QtEditorEngine::createBuiltinMeshes` and `GameMain`. Packaged games previously drew the cube and sphere at twice the editor size (half-extent 1.0, matching `.engine/meshes/Cube.obj`) while colliders authored in the editor use 0.5 extents. `GameMain`'s fallback that maps a missing `.engine/meshes/<Name>` file to `builtin://<name>` now logs a warning, because the builtin can differ in size from the missing file.

## FPS blocker fixes

- `Plugins/HephaestusFPS/Content/Scripts/FPS/Logic.lua:Logic.tickFire` — while a weapon cannot fire (reloading, empty, or an automatic trigger released) `nextFire` is held at no less than `now`. Before, `now` kept advancing and the next held frame paid back the gap as up to 4 shots in one frame (a 10 rps weapon re-pressed after 0.25 s fired 2). Catch-up still applies to a hitch while the trigger stays held. Covered by `engine/Tests/FPSLogicTests.cpp` (re-press after idle, fire after a held reload).
- `engine/Plugins/PluginContent.cpp:FindMissingEnabledPlugins` / `engine/Build/PackageStager.cpp:PackageStager::stage` — ids set `true` in `.hephaestus/plugins.json` with no manifest under `<engineRoot>/Plugins` or `<projectRoot>/Plugins` fail the package with `PACKAGE_PLUGIN_NOT_FOUND`, naming both folders. `CollectEnabledPluginContent` skips unknown ids, so a wrong engine root (`RuntimeLocator::discoverEngineRoot` falls back to the executable folder) used to produce a package without the FPS plugin's `Content`. Covered by `engine/Tests/PackageLayoutTests.cpp`.
- `engine/Physics/JoltPhysicsSystem.cpp:JoltPhysicsSystem::ApplyRenderInterpolation` / `RestoreSimulationPoses` — `Update` records each live character controller's position and each dynamic body's local position and Euler rotation before the last substep (`CaptureInterpolationStart`) and after it (`CaptureInterpolationEnd`). Hosts call `ApplyRenderInterpolation` after the simulation step and before camera sync and render (`engine/Game/GameMain.cpp:main` in realtime mode, `QtEditorEngine` tick while playing in realtime with physics up) and `RestoreSimulationPoses` straight after render, so scripts, automation and the next step only ever see stepped poses. The blend factor is `m_Accumulator / kPhysicsFixedDt`, so rendering trails the simulation by up to one step. An entity whose transform no longer equals the recorded stepped pose (teleport, script write) is skipped. Character rotation is excluded because scripts set facing every frame. Rotation blends per Euler component and is skipped when any component moves more than 90 degrees in a step. Covered by `engine/Tests/JoltPhysicsIntegrationTests.cpp` and `engine/Tests/CharacterControllerJoltTests.cpp`.
- `engine/Core/SimulationStep.cpp:RunSimulationStep` (physics exceptions) — every call reachable from `PrepareSceneBodies`, `JoltPhysicsSystem::Update`, `CharacterControllerSystem::FixedStep` and Lua contact dispatch was checked for throwing operations. `engine/Physics` has no `throw` outside `JoltPhysicsEngine::Initialize`. Mesh loading through `ModelImporter::LoadModel` catches its own parse errors. Filesystem calls use `std::error_code` overloads except `fs::current_path()`. Lua callbacks run under `lua_pcall`. A project root and mesh path outside the ANSI code page were tried in a scratch integration test, and nothing threw. Only allocation failure and `fs::current_path()` remain, so no physics exception source was found to fix, and the packaged game still lets one propagate to the crash handler. The editor's `onPhysicsError` was added during early Jolt integration with no recorded failure behind it.
- `engine/Physics/PhysicsWorldPose.h:PoseQuatToEulerXYZ` — extracts Euler angles for `q = qx * qy * qz` (the `R = Rx * Ry * Rz` order of `TransformComponent::GetLocalMatrix`, `SetFromMatrix` and `PoseQuatFromEulerXYZ`). It previously used the Z-Y-X formula, so `SyncTransformFromPhysics` and `TryComposeWorldPose` wrote the wrong rotation for any dynamic body turned about more than one axis (`(0.3, 0.4, 0.5)` came back as `(0.46, 0.19, 0.61)`). The unused, equally wrong `QuatToEulerXYZ` in `engine/Physics/JoltPhysicsSystem.cpp` was removed. Covered by `engine/Tests/PhysicsFoundationTests.cpp` (round trip and agreement with `SetFromMatrix`).

## Probe GI Phase 0: HDR scene target and tone mapping

- `engine/Gfx/VulkanSwapchain.cpp:VulkanSwapchain::initInternal` — the swapchain render pass has two subpasses. `kSceneSubpass` renders skybox and lit meshes into `hdrImage` (`R16G16B16A16_SFLOAT`) with the shared depth buffer. `kOverlaySubpass` reads `hdrImage` as an input attachment, tone-maps into the swapchain image, then draws grid, debug overlay, billboards, light gizmos, outlines, the transform gizmo and HUI against the same depth. The swapchain attachment uses `LOAD_OP_DONT_CARE` because the tone-map pass writes every pixel. One HDR image serves every frame in flight, so the external dependency into `kSceneSubpass` waits for the previous frame's colour/depth writes and fragment-shader input reads. The old dependency had `srcAccessMask = 0`, which ordered the shared depth image only by execution.
- `engine/Gfx/VulkanSwapchain.cpp:ChooseSurfaceFormat` — replaces `formats[0]`. It prefers `B8G8R8A8_UNORM`, then `R8G8B8A8_UNORM`, then the `_SRGB` variants, all with `SRGB_NONLINEAR`. Otherwise it keeps the first entry, and a lone `UNDEFINED` entry maps to `B8G8R8A8_UNORM`. Before, a driver that listed an `_SRGB` format first got gamma applied twice, because the shaders already applied `pow(1/2.2)`. Covered by `engine/Tests/SwapchainFormatTests.cpp`.
- `shaders/tonemap.frag` / `engine/Gfx/EngineFrameRenderer.cpp:EngineFrameRenderer::recordToneMap` — the only place that applies Reinhard and `pow(1/2.2)`. `triangle.frag` (lit and unlit) and `skybox.frag` now write linear HDR. The output matches the previous per-shader curve. On an `_SRGB` swapchain the shader decodes with the exact sRGB EOTF so the hardware encode lands on the same display value. Translucent materials now blend in linear HDR before tone mapping instead of after it, so overlapping translucent surfaces can look slightly different. Opaque output is unchanged: sampled sky, wall and floor pixels in the packaged FPS `Redline` scene were identical before and after.
- `engine/Gfx/EngineFrameRenderer.cpp:DisplayToSceneLinear` — `FrameRenderConfig::clearColor*` is a display colour, so the HDR clear value is its inverse tone map (capped at 0.999 before the Reinhard inverse), and the background looks the same as before.
- `engine/Gfx/EngineFrameRenderer.cpp:EngineFrameRenderer::createToneMapResources` — created in `Init` and on every swapchain recreation (it binds `hdrImageView`). A failure is fatal, as for `createPipeline`, because nothing else writes the swapchain image. Every pipeline built against `m_swapchain->renderPass` must pick its subpass. Scene pipelines (`VulkanPipeline::Init`, `createSkinnedMainPipelines`, `Skybox::CreatePipeline`) keep subpass 0. Overlay pipelines use `VulkanSwapchain::kOverlaySubpass`, and `VulkanHUIRenderer::Init`/`OnSwapchainRecreated` take it as a parameter.
- `engine/Gfx/EngineFrameRenderer.cpp:EngineFrameRenderer::prepareEnvironment` — the HDRI reload and `updateEnvironmentReflectionDescriptor` now run in `RenderFrame` before `vkBeginCommandBuffer`. They used to run inside `recordMainPass`, after the editor `recordIdPass` had already bound `m_descriptorSets[imageIndex]`. Writing binding 5 of a bound set, or destroying the old HDRI it pointed at, invalidated the command buffer every editor frame (validation: `VUID-*-commandBuffer-recording`, "destroy or updated without UPDATE_AFTER_BIND"). The packaged game has no ID pass, so it was not affected. `findEnvironment` is the shared Environment lookup used by both paths. Material texture slots were already deferred to `flushPendingTextureDescriptorUpdates` for the same reason.

## Probe GI Phase 1: sky irradiance

- `engine/Gfx/SkyIrradiance.cpp:ProjectEquirectIrradianceSH` — projects the HDRI to order-2 SH and pre-multiplies the clamped-cosine band factors, so `EvaluateIrradianceSH` (and `triangle.frag:evaluateSkyIrradiance`, which uses the same basis constants) returns irradiance. Texel directions match `triangle.frag:sampleEnvironmentReflection` for bottom-up rows (`VulkanTexture::LoadHDRFromFile` flips on load). It runs on the CPU in `EngineFrameRenderer::Skybox::LoadHDRI` from the pixels `LoadHDRFromFile` now hands back, so no GPU compute is needed yet; compute arrives with probe relighting in Phase 4. Covered by `engine/Tests/SkyIrradianceTests.cpp`.
- Sun exclusion (Andrew's decision, 2026-10-28): texels within 5 degrees of the brightest texel are skipped, because the scene's directional light already supplies the sun with shadows. In `studio_garden_1k.hdr` the sun reaches radiance ~1.1e5 and carries ~90% of the irradiance. Kept in, it double-counts the sun, and SH9 ringing drove faces turned away from it to zero (negative before the clamp). The result matches a clamp of the sun pixels within 0.03 on every axis. For an HDRI without a sun, this removes only one 5 degree cap (under 1% of the sphere). An HDRI scene with no directional light therefore gets no sun.
- `engine/Gfx/EngineFrameRenderer.cpp:EngineFrameRenderer::updateLightingUBO` — when the Environment HDRI is loaded and `useAsIBL` is set (the same condition as HDRI reflections), `environmentReflectionParams.z = 1`, `.w = hdriIntensity`, and `skyIrradianceSH[9]` is appended to `LightingUBO` after `cascadeSplits`. `triangle.frag` then uses `E(N) / pi * albedo * (1 - metallic) * ao` for ambient. Otherwise it keeps the old flat ambient, so scenes without an HDRI look the same as before. Scenes with an HDRI change look: shadowed faces now take the sky's colour and brightness.

## Probe GI Phase 2: probe volume component

- `engine/Scene/Components.h:ProbeVolumeComponent` — an axis-aligned grid centred on the entity's world translation. Entity rotation and scale are ignored, because DDGI probe grids are axis-aligned. `ProbeOffset` spreads `probeCount` probes from one face to the other on each axis, and a single probe on an axis sits at the centre. The editor overlay uses it now, and the Phase 3 bake and Phase 4 GPU layout must use the same formula. No bake-file path is stored yet; Phase 3 adds it together with the bake. Covered by `engine/Tests/ProbeVolumeTests.cpp`.
- `engine/Scene/SceneSerializer.cpp:WriteProbeVolumeJson` / `ApplyProbeVolumeJson` — written by both `Serialize` and `SerializeToString` and read by `Deserialize`, as `"ProbeVolume": { enabled, size, probeCounts: [x, y, z], intensity }`. Counts below 1 load as 1. Scenes without the key load unchanged.
- Like `EnvironmentComponent`, it is a scene-level lighting object. It is not in `PrefabComponentIO::SupportedTypes` or the automation `ComponentMetadataRegistry`, so `engine/UI/InspectorSelectionModel.cpp:BatchAddComponent` / `BatchRemoveComponent` and `EditorMainWindow` reset handle it directly, as they do Environment.
- `engine/UI/QtEditor/ProbeVolumeInspector.cpp` — enabled, size, probe counts (1-64 per axis), intensity, and a read-only total probe count, using the shared mixed-value helpers for multi-selection.
- `engine/UI/QtEditor/QtEditorEngine.cpp:AppendProbeVolumeDebugDraw` — draws each volume's box and a cross at every probe through the existing editor debug overlay (cyan when enabled, grey when disabled). The overlay is drawn only in the editor while not playing. It draws every probe, so a 64x64x64 volume uploads about 1.5M overlay vertices a frame. The packaged game loads the component but does not use it yet.

## Probe GI Phase 3: probe bake

- `engine/Gfx/ProbeBake.cpp:BakeProbeVolume` — CPU ray tracing on a median-split BVH, not the GPU cube capture the design page described. Hits are exact, it needs no new render passes, and it is unit-testable without a GPU. Each probe traces `kProbeBakeRaysPerProbe` (128) fixed spherical-Fibonacci directions (`ProbeRayDirection`; the Phase 4 GPU relight must use the same directions) and stores distance, oriented normal, material albedo and emissive per ray, or distance < 0 for sky. Probes are split across `std::thread::hardware_concurrency()` workers. Albedo is `MaterialComponent::albedo` only; albedo textures and vertex colours are not sampled, so textured surfaces bounce their tint colour.
- Relocation: a probe whose rays hit backfaces more than 25% of the time is treated as buried (the DDGI paper's threshold). It steps through the nearest backface by `distance + 5%` of the allowed offset, but only if that stays within `0.45 * spacing`, and it keeps the move only if fewer rays then hit backfaces. Offsets are stored per probe. This works only for closed, consistently wound meshes.
- `engine/Gfx/EngineFrameRenderer.cpp:EngineFrameRenderer::CollectProbeBakeGeometry` — world-space triangles from visible MeshRenderers that are not `hideInGame`, have no Character or CharacterController component, and have no non-static RigidBody. Skinned meshes are skipped. Materials come from `resolveMaterialForSlot`, now a member shared with `recordMainPass` instead of a lambda. CPU triangles exist only because `AddStaticMesh` keeps `MeshGPU::cpuPositions/cpuIndices` when `m_editorOverlays` is set (the editor), so packaged games pay no memory for them.
- `.hpprobes` v1 layout (v2 adds a uint64 geometry signature after the ray count; `ReadHeader` accepts both) (`WriteProbeBake` / `ReadProbeBake` / `ReadProbeBakeHeader`): magic `HPPB`, version, centre, size, int32 counts[3], rays; then a float3 offset per probe; then 24 bytes per ray (float distance, octahedral normal as 2 x snorm16, RGBA8 albedo, float3 emissive). An 8x4x8 volume is about 0.8 MB. The reader validates the counts (1-1024) and rays (1-4096) and rejects truncated files.
- `engine/UI/QtEditor/EditorMainWindow.cpp:EditorMainWindow::bakeProbeVolumes` — runs synchronously on the UI thread with a wait cursor, for the selected volumes. The scene must be saved in a project. The file goes next to the scene as `<scene>.<tag>_<entity id>.hpprobes`, and `ProbeVolumeComponent::bakePath` stores it project-relative (serialized as `bakePath`, with an undo snapshot). `PackageStager` copies the whole `assets/` tree, so the file ships without packaging changes.
- `engine/UI/QtEditor/ProbeVolumeInspector.cpp:Refresh` — status comes from `ReadProbeBakeHeader` plus `ProbeBakeMatchesVolume`: not baked, unreadable, out of date (counts, size or centre changed), or baked. A geometry change is reported when the current `ProbeBakeGeometrySignature` differs from the one stored in the file (see below).
- `engine/Gfx/ProbeBake.cpp:ProbeBakeGeometrySignature` — the sum of a per-triangle FNV-1a hash over world positions plus material albedo and emissive. Summing makes it independent of entity iteration order, which changes when unrelated components are added or removed. It never returns 0, so 0 means "unknown": version 1 files load with signature 0, and the inspector asks for a re-bake instead of warning. `engine/UI/QtEditor/EditorMainWindow.cpp:rebuildComponentInspectors` gives `ProbeVolumeInspector::SetGeometrySignatureProvider` a lambda that runs `CollectProbeBakeGeometry` on every inspector refresh. That is proportional to the scene's static triangle count, so it shows up only while a probe volume is selected. The warning appears the next time the volume's inspector refreshes; editing other entities does not update an inspector that is already open.

## Probe GI Phase 4: GPU probe relighting

- `engine/Gfx/ProbeGI.cpp:ProbeGI::Prepare` — finds the first enabled `ProbeVolumeComponent` with a `bakePath`, resolves it against `EngineFrameRenderer::m_projectRoot` (then as given), and reloads when the path, the file's write time or the entity changes. A failed load is logged once and not retried until one of those changes. The GPU grid comes from the bake header (centre, size, counts), not the current component values, because the rays belong to that grid. Only `enabled` and `intensity` are read live. Bakes must have `kProbeBakeRaysPerProbe` (128) rays, which is the compute workgroup size. Multiple volumes are not supported yet: only the first is lit.
- `shaders/probe_update.comp` — one workgroup per probe, one invocation per ray, and every probe is updated every frame. Each ray's radiance is computed from the baked hit as `albedo / pi * (direct + bounce) + emissive`. Direct light is the sun (occlusion from the probe sun map) plus point and spot lights (unshadowed). Bounce is `sampleProbeIrradiance` from the previous frame's atlases, which gives multiple bounces over time. A ray that reached the sky uses `E_sky(dir) / pi` from the sky SH (sun excluded) when the HDRI is used for IBL, otherwise the flat ambient colour. Rays are then blended in shared memory into an 8x8 irradiance tile (cosine-weighted mean radiance, i.e. irradiance / pi) and a 16x16 visibility tile (mean distance and distance squared, cos^50 weighted, clamped to 1.5x the probe spacing). Hysteresis is 0.97, and the first frame after a load discards history. Border texels are computed directly from the direction across the octahedral fold, so no separate border pass is needed.
- Atlases (`RGBA16F` and `RG16F`, `probeCountX * probeCountY` tiles wide by `probeCountZ` tall) exist twice and alternate each frame: compute reads `[parity]` and writes `[1 - parity]`, and drawing samples `[1 - parity]`. Each swapchain image has two descriptor sets (compute and draw), rewritten in `Prepare` before recording, while that image's fence is already signalled. All atlases stay in `VK_IMAGE_LAYOUT_GENERAL`. `RecordUpdate` places a global memory barrier from earlier compute and fragment work to compute before the dispatch, and one from compute to vertex and fragment shaders after it.
- `engine/Gfx/EngineFrameRenderer.cpp:recordProbeGISunPass` — a 2048x2048 depth map over the bake's bounding sphere (radius = half the volume diagonal + max ray distance), oriented along the first shadow-casting directional light (`FindShadowCastingSun`). It draws only `IsProbeStaticMesh` geometry, the same filter the bake uses, with the CSM depth-only render pass and pipeline, plus explicit barriers (compute read to depth write before, depth write to compute read after), because that render pass's own dependencies only cover fragment-shader reads. Without a shadow-casting sun, `giParams.y = 0` and the sun is unoccluded for the probes. Note that the lighting UBO takes the last enabled directional light while the sun map uses the first shadow-casting one; they match in scenes with one sun.
- `shaders/probe_common.glsl:sampleProbeIrradiance` — DDGI-style trilinear blend of the 8 surrounding probes with a wrap-shading backface weight and a Chebyshev visibility test (cubed, floored at 0.05). Phase 5 uses the same function for surface shading. `shaders/lighting_common.glsl` now holds the lighting UBO and the light helpers previously inside `triangle.frag`, so the compute relight uses the same attenuation, spot falloff and sky SH code. The CMake shader commands depend on both include files.
- `ProbeGI::RecordDebug` — in the editor and outside Play, every probe is drawn as a sphere (generated in `shaders/probe_debug.vert`) in the scene subpass, shaded by its own irradiance for the sphere normal. Check (2026-10-28): a scratch Cornell box with 4x4x4 probes shows red on the wall-facing side of the probes beside the red wall and green beside the green wall.
- GPU time from timestamps around the sun map and dispatch: `FrameStats::probeGIGpuMs`, and logged every 600 frames as `[ProbeGI] N probes updated in X ms GPU`. Measured on Andrew's Redline bake (450 probes): about 0.11 to 0.13 ms, with one 1.1 ms reading. Timing is skipped when the graphics queue reports no timestamp bits.

## Probe GI Phase 5: surfaces lit by probes

- `shaders/triangle.frag` — when `gi.probeCounts.w == 1`, the diffuse ambient term becomes `sampleProbeIrradiance(worldPos, N) * intensity * albedo * (1 - metallic) * ao`, faded into the previous sky or flat ambient over one probe spacing outside the volume's probe bounds. Direct lighting, shadows and specular reflections are unchanged. The skinned pipeline uses the same fragment shader, so animated characters receive probe light too (they still do not block or bounce it).
- The probe set is set 2 of both surface pipelines. `VulkanPipeline::Init` takes `extraSetLayouts`, and the main layout is `[main, ProbeGI::EmptySetLayout, ProbeGI::SetLayout]`. The skinned layout is `[main, bones, ProbeGI::SetLayout]`. Set 2 is therefore not compatible between the two layouts, so `recordMainPass` rebinds `ProbeGI::DrawSet(imageIndex)` whenever the draw layout changes (`probeSetLayout`).
- Because every lit draw binds the probe set, `ProbeGI::Init` (layouts plus 1x1 placeholder atlas and buffer) and `CreateSwapchainResources` now fail `EngineFrameRenderer::Init` or swapchain recreation if they fail. The probe update pipeline, sun map, timing queries and debug pipeline stay optional. `ProbeGI::Prepare` always rewrites the image's sets: placeholders with zeroed parameters (`probeCounts.w = 0`) when no volume is loaded. `ProbeGI::Init` runs before `createPipeline` so the layouts exist. `ProbeGI::Shutdown` moved to the end of `destroyAllResources`, after the pipeline layouts that reference its set layouts.
- Check (2026-10-28): in the scratch Cornell box the floor next to the red wall reads (195,186,181) against (188,193,180) next to the green wall, and the back wall's left and right edges tint the same way. In the packaged Development build of Redline with Andrew's bake, the frame matches the old build within a few levels (the shadowed wall loses some of the flat ambient's blue). Validation shows only the existing semaphore error in both the editor and the packaged game.

## Probe GI Phase 6: hardware ray tracing toggle

- `engine/Gfx/VulkanDevice.cpp:VulkanDevice::createLogicalDevice` — when the device reports Vulkan 1.2+ and `VK_KHR_acceleration_structure`, `VK_KHR_ray_query` and `VK_KHR_deferred_host_operations`, and the `bufferDeviceAddress`, `accelerationStructure` and `rayQuery` features, it enables them through a `VkPhysicalDeviceFeatures2` chain (instead of `pEnabledFeatures`) and loads the five KHR entry points into `RayTracingFunctions`. `createAllocator` (now shared by both init paths) then sets `VMA_ALLOCATOR_CREATE_BUFFER_DEVICE_ADDRESS_BIT` with `vulkanApiVersion = 1.2`. Other GPUs create the device exactly as before. `EngineFrameRenderer::AddStaticMesh` adds device-address, storage and acceleration-structure-input usage to mesh buffers only when `SupportsRayQuery()`.
- `ProbeVolumeComponent::hardwareRayTracing` (serialized `hardwareRayTracing`, default false; inspector "Ray Tracing" group) — when set on a GPU where `ProbeGI::HardwareRayTracingAvailable()`, the volume needs no bake. `ProbeGI::createHardwareVolume` makes a GPU-only hits buffer (same `GpuRayHit` layout as an uploaded bake) and zero probe offsets, the grid follows the component and entity live, and only a probe-count change rebuilds. Without support the volume falls back to its bake, and with no bake either it is not lit. The inspector says which applies.
- `engine/Gfx/ProbeRayTracer.cpp` — one BLAS per non-skinned `MeshGPU`, built synchronously the first time an instance uses it and keyed by its vertex buffer handle. BLASes are freed only at shutdown, so a mesh reloaded under a new buffer leaves its old BLAS behind until the editor closes. Each swapchain image has its own TLAS, instance buffer, per-instance data (albedo, emissive, vertex and index buffer addresses) and scratch buffer, grown with a device wait when the instance count exceeds capacity. `Record` rebuilds the TLAS every frame (fast build, all visible non-skinned meshes including dynamic bodies, material from slot 0 only), then runs `shaders/probe_trace.comp`.
- `shaders/probe_trace.comp` — writes the same per-ray hits as the bake: geometric normal from the triangle's three vertices fetched through `GL_EXT_buffer_reference` and transformed by the instance's object-to-world inverse transpose, plus the albedo and emissive of slot 0. It also traces a sun shadow ray per hit and stores the visibility in `albedo.w`. `probe_update.comp` uses that instead of the static-only sun map when `giParams.w = 1`, so moving objects shadow the sun for the probes too. Compiled with `--target-env=vulkan1.2` (a per-file flag in the CMake shader loop). `probeRayDirection` moved to `probe_common.glsl` and is shared with `probe_update.comp`.
- Skinned characters are still excluded from tracing, because skinning happens in the vertex shader. Point and spot lights remain unshadowed for the probes.
- Check (2026-10-28, RTX 5090): the scratch Cornell box traced with no bake matches the baked result within 1 level per channel. With a dynamic emissive crate added, the traced box tints the red wall beside it from (190,75,67) to (215,84,63), while the bake ignores the crate as intended. Redline traced (450 probes) logged 0.18 ms and 1.37 ms GPU in two samples. The packaged Development build enables ray queries and renders the traced Redline. Validation shows only the existing semaphore error. Movement during Play was not checked frame by frame; the TLAS is rebuilt from current transforms every frame.
- `engine/UI/QtEditor/PropertyEditors.cpp:SetCheckFromMixed` — sets the checkbox tristate only for a mixed or empty selection. ## Probe GI: blotchy shading fixes (2026-10-28)

Andrew saw dark blotches on shadowed walls in Redline, both baked and traced. His volume was 100x20x100 m with 15x8x8 probes (about 7 m by 2.9 m by 14 m spacing). Three causes were fixed:
- Backface hits: `ProbeRayHit::backface` (bake: alpha byte of the stored albedo, so version 2 files keep loading; GPU: `emissive.w`; trace: from the winding of the hit triangle before the normal flip). `probe_update.comp` gives backface rays zero radiance and 0.2x distance, as in DDGI. Before this, a probe inside a wall saw the inside of the wall lit as if it were a front face and leaked that through the wall. Winding is taken as the visible side, matching `backfaceCulling`, which holds for the builtin cube (counter-clockwise from outside). Covered by `engine/Tests/ProbeBakeTests.cpp` (buried single probe and room front faces).
- Surface bias: `probe_common.glsl:sampleProbeIrradiance` takes a view direction and offsets the lookup position by `(0.2 n + 0.8 v) * 0.75 * minSpacing * 0.3`, the DDGI paper's bias, instead of `0.05 * maxSpacing` along the normal only. `triangle.frag` passes `V`, and the compute bounce passes `-dir`.
- Fixed ray directions: traced volumes rotate all 128 directions by a new uniform random rotation every frame (`ProbeGI.cpp:RandomRotation`, `ProbeGIParams::rayRotation`), shared by the trace and update passes so hits and directions agree. Hysteresis then averages over many directions. Baked volumes keep the identity rotation because their hits belong to the fixed directions.
- Density still matters: with the fixes, the coarse grid still shows faint blotches, and 40x8x40 (about 2.5 m spacing, 12,800 probes) is visibly smoother. The Cornell box values are unchanged to within one level.

## Sun shadow bias (2026-10-28)

- `shaders/triangle.frag:sampleDirectionalShadow` — the depth bias used to be `LightComponent::shadowBias` as a fraction of the cascade's NDC depth range, plus a slope term of up to 5x that, times up to 3.25x for far cascades. The cascade depth range is `max(radius, 10) + 2 * radius + 1` (`engine/Core/Math.h:ComputeCascadeShadowVP`), so the bias grew to tens of centimetres even in the nearest cascade and to metres in far ones. That lit a strip of floor along every wall base in shadow (Andrew's report). It is now sized from the cascade's texel footprint: the receiver is offset along its geometric normal by `texelWorld * (0.5 + 1.5 * (1 - N.L)) + shadowNormalBias`, and the depth bias is `(texelWorld + shadowBias) / depthRange`. `ComputeCascadeShadowVP` reports the radius and depth range through optional out parameters, and `LightingUBO` gains `cascadeTexelWorld`, `cascadeDepthRange` and `shadowBiasWorld` (appended, also in `shaders/lighting_common.glsl`).
- `LightComponent::shadowBias` and `shadowNormalBias` are now extra world-space metres on top of the automatic bias. "Normal Bias" was shown in the Light inspector and saved, but never used by the renderer before this.
- Check: in the packaged Redline start view, the bright line along the base of the right wall is gone (contrast-boosted crops). The rest of the frame is unchanged in the sampled regions.

## Point and spot light shadows (2026-10-28)

- `engine/Gfx/EngineFrameRenderer.cpp:createLocalShadowResources` makes one D32 atlas (`m_localShadow`, 4096x2048, 8x4 tiles of 512) that reuses `m_directionalShadow`'s render pass, pipelines and sampler, so static and skinned casters need no new pipelines. The image is moved to `SHADER_READ_ONLY_OPTIMAL` once so frames without shadowed lights can still bind it at set 0 binding 6 (`engine/Gfx/VulkanPipeline.cpp`).
- `EngineFrameRenderer::updateLightingUBO` hands out tiles in light order: six for each point light (+X,-X,+Y,-Y,+Z,-Z, 90 degree faces), one for each spot (FOV = outer cone + 0.1 rad, capped at 2.8). Limits are `kMaxShadowedPointLights` (4) and `kMaxShadowedSpotLights` (8): 4*6+8 = 32 tiles. `LightingUBO` appends `localShadowViewProj[32]`, `pointShadowParams[16]` and `spotShadowParams[16]` (x = tile or -1, y = `shadowStrength`, z = range as far plane, w = tan(half FOV)); the near plane is the constant `kLocalShadowNear` (0.05) mirrored in the shader.
- `EngineFrameRenderer::recordLocalShadowPass` draws each tile with its own viewport and scissor through `drawShadowCasters`, which is the old per-cascade mesh loop from `recordShadowPass` plus an optional bounding-sphere cull against the light range.
- `shaders/triangle.frag:localShadow` compares in linear depth so the bias is in metres: normal offset of `texelWorld * (0.5 + 1.5 * (1 - N.L))` (the same shape as the sun) and a receiver pull of 1.5 texels, where `texelWorld = 2 * dist * tan(halfFov) / 512`. PCF taps are clamped inside the tile so neighbours never bleed in. `pointShadow` picks the cube face by the major axis.
- Check: ShadowTest Cornell scenes in the editor with identical cameras, Cast Shadows on vs off. The point light's crate shadow lands on the floor and red wall, attached at the base; the spot light cuts the crate's top edge out of its cone. Off renders the same as before. ## Sun cascade blending and fade (2026-10-28)

- `shaders/triangle.frag:cascadeOcclusion` is the old per-cascade body of `sampleDirectionalShadow` (bias, projection, 16-tap rotated Poisson PCF), returning the fraction of taps in shadow. Taps are now clamped to the cascade's own atlas quadrant; before, wide filters at a cascade's border sampled the neighbouring cascade's depth.
- `shaders/triangle.frag:sampleDirectionalShadow` picks the cascade by view depth as before, then over the last 10% of that cascade's depth range mixes in the next cascade's occlusion, and over the last 10% of cascade 3 fades occlusion to zero. Fragments beyond `cascadeSplits.w` return fully lit without sampling. Fragments in a blend band cost two cascade lookups.
- Check: Redline editor A/B with the previous shader (identical camera). Pixels differ only in a narrow band near a cascade boundary on a distant wall, where the shadow edge softens.

## Soft sun shadows (PCSS) and sun size (2026-10-28)

- `LightComponent::sunAngularDiameter` (degrees, default 1) is saved as `shadow.sunSize` by both writers in `engine/Scene/SceneSerializer.cpp` and read back in the light loader, and as `sunAngularDiameter` by `engine/Scene/PrefabComponentIO.cpp` capture/apply. `engine/UI/QtEditor/LightInspector.cpp` shows it as "Sun Size" for directional lights only (`updateTypeVisibility`).
- `EngineFrameRenderer::updateLightingUBO` puts `tan(clamp(diameter, 0, 10) / 2)` in `shadowBiasWorld.z`.
- `shaders/triangle.frag:cascadeOcclusion` replaces the fixed per-cascade spread (2.5 + cascade texels, so penumbrae jumped in size at each cascade) with PCSS: a 16-tap blocker search over `tan(halfSun) * 4 m` (clamped to 1.5..24 texels), then the penumbra is `blockerDistance * tan(halfSun)` in metres (blocker distance from the average blocker depth times `cascadeDepthRange`), converted to texels with `cascadeTexelWorld` and clamped to 1.5..24, and filtered with the same rotated 16-tap Poisson disk. No blocker found means fully lit without the second pass. The 4 m search cap limits how soft shadows from tall casters can get; the 24-texel cap does the same at the near cascade.
- Check: `LightShadowSettingsTests` covers the default, scene and prefab round trips and a scene saved without the field. Redline editor captures (same camera): contact shadows at the crate base are sharper than with the fixed spread, the far end is still soft, and Sun Size 4 visibly widens the far penumbra.

## Content Browser thumbnails (2026-11-04)

- `engine/Assets/AssetThumbnailRenderer.cpp:RenderThumbnail` — a CPU rasterizer, not the Vulkan renderer: `EngineFrameRenderer` only draws into the swapchain of a viewport window, so there is no offscreen target to render previews into. It rasterizes at 2x and box-filters down, with a z-buffer and perspective-correct barycentrics, shading each pixel once afterwards. `Shade` ports `shaders/triangle.frag`'s lit path (GGX, Smith, Schlick, F0 from `specular`, the 0.7 normal-map blend, the reflection term, emissive) and `shaders/tonemap.frag` (Reinhard, gamma 2.2), and samples textures decoded from sRGB like the engine's `VK_FORMAT_R8G8B8A8_SRGB` views. Scene lights, shadows, sky irradiance and probe GI are replaced by a fixed two-light rig, a hemisphere ambient and a gradient backdrop for reflections; world-aligned (triplanar) UVs are not reproduced. Triangles whose material discards (`opacity < opacityMask`) are skipped. Keep `Shade` in step with `triangle.frag` when the material model changes.
- `engine/Assets/AssetThumbnailRenderer.cpp:RenderAssetThumbnail` — materials render on `BuildBuiltinMesh("builtin://sphere")`; meshes load through `ModelImporter::LoadModel`; prefabs are instantiated into a private `Scene` with `PrefabInstantiator::Instantiate` (no instance component), and each visible `MeshRendererComponent` draws at `Scene::GetWorldTransform` with `appliedMaterialPaths[slot]`, else the node's `MaterialComponent`, else the default material. Character (skinned) prefabs and meshes that do not resolve draw nothing, so the card keeps its type icon. Paths resolve through `AssetPathPolicy::ResolvePortableKey`, then relative to the asset root. That reads `AssetMountRegistry` from the worker thread without a lock; mounts only change when plugins are enabled or disabled.
- `engine/Assets/AssetThumbnailRenderer.cpp:LoadThumbnailImage` — uses `stb_image` like `VulkanTexture`, and sets `stbi_set_flip_vertically_on_load_thread(0)` because `VulkanTexture::LoadHDR` toggles the global flip flag on the render thread. Material textures are halved to at most 512 px before sampling.
- `engine/UI/QtEditor/AssetThumbnailCache.cpp:AssetThumbnailCache::Thumbnail` — work runs on the cache's own `QThreadPool` (2 low-priority threads) and results come back to the UI thread through a queued `invokeMethod`; the destructor clears and waits for the pool, so no job outlives it. A cache file is used only when every dependency still matches. `AssetBrowserWidget::rebuildContentsView` calls `Invalidate`, so every rebuild (navigation, filters, search, `Refresh`) rechecks the visible assets in the background while the previous image stays on the card; `CancelPending` drops queued work for the folder being left. ## Steam release preparation

- `engine/Build/PackageStager.cpp:LicenseNotices` — packaged games get `ThirdPartyNotices.txt` as a byte copy of `<engineRoot>/THIRD_PARTY_NOTICES.md`. ## FPS gunplay (Slice 1 firing range)

- `engine/Gfx/EngineFrameRenderer.cpp:EngineFrameRenderer::recordMainPass` — in play, meshes with `MeshRendererComponent::viewModel` are drawn with `MakeCameraViewFrame(render camera) * inverse(active camera entity world) * entity world`, so the part of their transform below the camera entity is read in the render camera's frame (+X forward, +Y up, +Z right). World draws use viewport depth `[0.05, 1]` and view models `[0, 0.05]`, so world geometry can never cover a view model; the viewport goes back to `[0, 1]` before overlays. View models are skipped by `drawShadowCasters`, the probe trace instances and `IsProbeStaticMesh`. Outside play (editor viewport) they draw at their scene pose. Scripts that need a view model's world position (muzzle effects) must apply the same frame; their scene world transform is not where they are drawn.
- `engine/Scene/ActiveCameraSync.cpp:MakeCameraViewFrame` — the one definition of the render camera's world frame, matching `Mat4::LookAt` with world up. It replaces the hand-written conversion `Weapon.lua:tick` used to do because a camera entity's scene transform pitches about X while the render camera pitches about its right axis. Cameras keep their existing local rotation convention, so saved scenes are unchanged. Covered by `engine/Tests/ActiveCameraSyncTests.cpp`.
- `engine/Scene/ActiveCameraSync.cpp:MakeViewModelFovAdjust` — `CameraComponent::viewModelFov` without a second projection or pipeline: projected x and y are the focal length times view-space x and y, so scaling view-space x and y by `tan(fov/2) / tan(viewModelFov/2)` (in world space as `inverse(view) * scale * view`) gives the same clip x, y and w as projecting with `viewModelFov`. Depth is unchanged because z is not scaled. `EngineFrameRenderer::recordMainPass` multiplies it onto `viewModelRebase`, so it also applies to view model normals; the scale is uniform in x and y and the lighting difference is negligible at these ratios. Covered by `engine/Tests/ActiveCameraSyncTests.cpp:TestViewModelFovAdjust`. The key is `viewModelFov` in both the scene (`SceneSerializer.cpp`) and prefab camera (`PrefabComponentIO.cpp:CaptureCamera`) formats; scene cameras use `near`/`far`, prefabs `nearPlane`/`farPlane`.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Weapon.lua:updatePose` — reload dip and raise rotate the rig about a point `SHOULDER_REACH` (0.4 m) behind the weapon origin instead of the origin itself. The rig is rigid, so with full-length arms a rotation about the grip swung the upper arms and the arm cut through the camera. Rolling toward the left (negative roll) keeps the left shoulder down; a right roll lifts it into view.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Gunplay.lua:dampedSpring` — closed-form solution of the damped spring for a constant target over `dt` (under-, critically and over-damped branches), replacing the 240 Hz sub-stepped `springStep`. Splitting a frame differently gives the same result, which is what keeps kick, sway and the camera kick identical at 30 and 240 fps. `impulseForPeak` inverts the impulse response so data files give kick as a peak displacement; the old `value * 25` velocity on the 260/22 spring maps to a peak of `value * 25 * 0.02887`, the factor used when the firing range weapons moved to data files. `FPS-Shooter/assets/scripts/range/SteelTarget.lua` used `springStep` and now uses `dampedSpring(…, 9.487, 0.316, …)`, the same spring. Covered by `engine/Tests/FPSLogicTests.cpp`.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Gunplay.lua:hash01` / `seededRandom` / `rngNext` — integer hash (Lua 5.4 integers, masked to 32 bits) so recoil jitter depends only on `recoilSeed` and the shot number in the string, and spread on the weapon's own stream. Nothing in the plugin calls `math.random` for gameplay any more.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Logic.lua:tryStartReload` / `advanceReload` / `interruptReload` / `spendShot` — weapons hold `magazine` plus `chamber` (0/1). A reload is a list of timed events applied in order as `reloadElapsed` crosses them, so one long frame still applies detach, insert and chamber in sequence; ammo moves at `insert`, not at the end. Interrupting just drops the remaining events, which is what makes "cut after insert" leave an empty chamber and the next action a short `chamber` rack. Firing requires `chamber`, so `tickFire` checks it instead of `magazine`; `Registry.weaponSnapshot` reports magazine + chamber. Old weapons without `tacticalReload`/`emptyReload` tables get their event times from `reloadSoundTime`, `reloadPart2Time` and `boltTime` in `Weapon.lua:Weapon.register`.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Weapon.lua:Weapon.register` — `definition` names a Lua module found through the project's `assets/scripts` on `package.path` (`LuaScriptEngine` adds it). Precedence is register options, then the data file, then the script's exposed variables; the exposed defaults cannot be told apart from authored values, so a data-file weapon should keep only `definition` on its entity. A missing module prints `[FPS] Weapon definition … could not be loaded` and falls back to the variables.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Player.lua:updateCameraKick` / `applyCameraRotation` — the camera kick is added to the camera entity's local rotation (pitch and yaw) but `Logic.aimRay` still uses the unkicked `pitch`/`yaw`, so it is presentation only. The render camera reads local yaw through `ActiveCameraSync.cpp:TryMakeCameraView`, and the view model frame follows it. Weapons queue impulses in `Registry.player.cameraImpulses`; the player consumes them after the weapon tick in `onLateUpdate`.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Player.lua:updateFootsteps` — counts strides even with no footstep sounds, and `bobPhase` is `pi * (steps + fraction)`, so the bob's low points and the footfall dips land on the footstep sounds.
- `engine/Scene/PrefabComponentIO.cpp:CaptureMeshRenderer` / `engine/Scene/SceneSerializer.cpp:WritePrefabInstance` — both write paths through `AssetPathPolicy::ToPortableKey` (marker remap, no project root needed), the same rule `SceneSerializer.cpp:NormalizeAssetPathForSave` uses for plain entities. Live `meshAssetPath` is absolute after import and `CreateFromSelection` gets an absolute destination, so prefabs and prefab instances were saved with machine paths. Overrides compare captures on both sides, so an absolute live path is not an override of the portable prefab value. The filename fallback of `NormalizeAssetPathForSave` is deliberately not used for prefab paths, because a bare filename would not resolve. Material, script and audio paths in captures are stored as authored and were already portable here. Covered by `engine/Tests/PrefabSystemTests.cpp:TestCreatedPrefabPathsArePortable`.
- `engine/Automation/SceneAutomation.cpp` `prefab.create` — wraps `PrefabOverrideSystem::CreateFromSelection` like `EditorMainWindow::createPrefabFromSelection`, with the path resolved by `Content::ResolveAssetPath` (under the asset root, `.hpprefab`, never overwriting). Covered by `engine/Tests/AutomationSceneTests.cpp`.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Weapon.lua:updatePose` ADS pose — the weapon is rotated by `sightPitch`/`sightYaw` (applied as `Ry(yaw) * Rz(pitch)`, the order `TransformComponent::GetLocalMatrix` composes them) and then translated so the rotated point `(0, sightUp, sightRight)` lands on the view axis `adsForward` ahead. Before, ADS only translated, so a sight line not parallel to the weapon's X axis could not be centred: the firing range rifle's aperture-to-post line rises 2.65 mrad and drifts 0.93 mrad left, and with the old data (which also had `sightRight` mirrored) the post sat about 15 px off the aperture centre at 3168x1332. - `engine/Assets/FbxDocument.cpp:ReadFbxMaterials` — a `ShininessExponent` texture is glossiness for FBX SDK exporters (Mixamo files name it `*_Glossiness.png`), but Blender's exporter writes its roughness map there and its importer reads it back as roughness. ufbx reports both as `pbr.roughness.texture`, so the exporter decides: Blender files keep it as roughness, others go to `glossinessTexture`. `engine/Assets/CharacterImport.cpp:WriteRoughnessFromGlossiness` treats the map as scaling the FBX `ShininessExponent` value and writes `1 - sqrt(exponent * gloss) / 10` per texel (the conversion ufbx and Blender apply to the exponent itself) as a one-channel PNG; a plain `1 - gloss` made Mixamo's hard parts (gloss about 0.7) mirror-like (stb_image_write, static so it cannot clash with `ViewportAutomation.cpp`'s copy) and sets the material roughness factor to 1, since `triangle.frag` multiplies factor and map. Covered by `engine/Tests/AutomationCharacterTests.cpp` with `skinned_textured.fbx` and `skinned_textured_fbxsdk.fbx` (the same file with its creator string changed to an FBX SDK one).
- `engine/Gfx/VulkanTexture.cpp:LoadHDRFromFile` / `shaders/triangle.frag:sampleEnvironmentReflection` — the skybox HDRI gets a CPU box-filtered mip chain (RGBA32F blits are not guaranteed to filter), and reflections read mip `roughness * (levels - 1)`, so rough surfaces reflect a blurred sky instead of a sharp one dimmed by `(1 - roughness)^2`. `shaders/skybox.frag` samples level 0 explicitly so the equirect seam does not pick a tiny mip. This is still not a prefiltered GGX environment; a box-filtered equirect mip is an approximation that is wider than GGX near the poles.

## Audio engine (miniaudio)

- `engine/Audio/AudioEngine.cpp:AudioEngine::Impl` — miniaudio's `ma_engine` with one `ma_sound_group` per bus and `master` as the engine volume. `Impl::Cached` keeps one never-started `ma_sound` per file loaded with `MA_SOUND_FLAG_DECODE`, so the resource manager keeps the decoded data alive; each play is `ma_sound_init_copy` of it, which shares the decoded buffer instead of reading the file. Without the template the data would be freed when the last voice ended and the next shot would decode the file again. The cache is never trimmed; every file a session plays stays in memory until `Shutdown`.
- `engine/Audio/AudioEngine.cpp:AudioEngine::Impl::ApplyVoiceVolume` — voices are created with `MA_SOUND_FLAG_NO_SPATIALIZATION` and the engine sets volume and pan itself from `engine/Audio/AudioMath.cpp:Spatialize`, so the falloff and panning are plain functions covered by `engine/Tests/AudioEngineTests.cpp` and do not depend on miniaudio's coordinate conventions. The listener is set every simulation step from `ActiveCameraSync.cpp:MakeCameraViewFrame` in `engine/Core/SimulationStep.cpp:UpdateSceneAudioSources`, which also calls `AudioEngine::Update` to release finished voices and re-pan 3D ones. Panning is stereo balance, so 3D sounds behind the listener are not distinguished from sounds in front.
- `engine/Audio/AudioMath.cpp:ChooseVoiceToSteal` — when the budget (`Options::maxVoices`, 48) is full, finished voices are released first, then the lowest priority, quietest (volume x falloff x bus), oldest voice is replaced; a sound never replaces a voice of higher priority and is dropped instead (`Play` returns `InvalidHandle`).
- `engine/Audio/AudioEngine.h:AudioEngine::Options::nullDevice` — uses miniaudio's null backend so `AudioEngineTests` play real sounds without an output device. The null device still mixes in real time, so the test sleeps for the tone to finish.
- `engine/Audio/MiniaudioImplementation.c` — the single translation unit that compiles miniaudio, as C. `CMakeLists.txt` links CoreFoundation, CoreAudio and AudioToolbox on macOS and `dl`, `m`, `pthread` on other Unix; WinMM is no longer linked anywhere. The macOS path has not been built or heard yet.
- `engine/Automation/SceneAutomation.cpp` `audio.get_status` — reads the host's `AutomationBackend::Audio()`. Only the editor backend returns its `AudioEngine` (created at the first Play by `QtEditorEngine`), so before Play and in packaged games with automation the tool reports the host as unavailable.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Weapon.lua:playShot` — `fireLayers` from the weapon's data plays every layer of a shot at priority 10 on the `weapons` bus; reload sounds use priority 5 and footsteps (`Player.lua:updateFootsteps`) priority 1 on `sfx`, so a full budget drops footsteps before gunshots. The firing range weapons have one layer each because the asset library has no separate transient, mechanical or tail recordings.

## Translucent materials, muzzle flashes and decals

- `engine/Gfx/EngineFrameRenderer.cpp:EngineFrameRenderer::recordMainPass` — submeshes whose material `blendMode` is not `Opaque` are collected in `translucentDraws` instead of drawn, then drawn after every opaque surface with `VulkanPipeline::GetTranslucentPipeline`: world surfaces first and view models last (they are always nearer, in their own depth range), each sorted far to near by the distance from `m_frameCameraPos` to the model origin. Sorting is per object, so overlapping large translucent meshes can still sort wrongly. Skinned meshes are never deferred and draw opaque. `drawShadowCasters` skips a mesh whose slot 0 material is translucent; `IsProbeStaticMesh` does not check materials, so a translucent static mesh is still drawn into the probe sun map and baked.
- `engine/Gfx/VulkanPipeline.cpp:VulkanPipeline::Init` — `pipelineAlphaBlend` (src alpha, one minus src alpha) and `pipelineAdditive` (one, one) share the main shader and layout, cull nothing, test depth with `LESS_OR_EQUAL` and write none. Both keep the destination alpha.
- `shaders/triangle.frag` — the material's `blendMode` uses the UBO word that was `paddingTail[0]` (offset 128), so `MaterialUBO` keeps its size. For blended modes, opacity is multiplied by the albedo texture's alpha and fragments below 0.002 are discarded; additive returns `(albedo + emissive * strength) * opacity` before lighting. `shaders/*.spv` in the repository are not rebuilt by this change; the build compiles the shaders into `build/<config>/shaders`.
- `engine/UI/MaterialEditor/MaterialAssetSerializer.cpp` — reads and writes `blendMode` so a Material Editor save keeps it; the editor has no control for it yet.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Impacts.lua:rotationForNormal` — Euler angles for `Rx * Ry * Rz` (the order `TransformComponent::GetLocalMatrix` uses) with y = 0: `z = asin(-n.x)`, `x = atan2(n.z, n.y)`. A decal therefore has no random spin about the normal; variety comes from the three textures. `surfaceOffset` lifts decals by 2 mm plus 0.2 mm per metre of distance because the 0.02 m near plane leaves about 7 mm of depth resolution at 50 m. Covered by `engine/Tests/FPSLogicTests.cpp`.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Weapon.lua:applyHit` — decals are skipped on entities with health or a hit zone, because those targets swing or fall and a decal would be left floating; decals are not parented to what they hit.

## Particles

- `engine/Scene/ParticleSimulation.cpp:StepEmitter` — CPU simulation in world space on the emitter component itself (`ParticleEmitterComponent::particles`). Emission keeps a fractional carry, and each particle emitted inside a step is pre-aged by how long before the end of the step it was due, so counts and positions do not depend on how time is split into frames (`engine/Tests/ParticleSimulationTests.cpp`). The random stream is a per-emitter xorshift seeded from `seed`, so an emitter replays identically. `UpdateScene` runs once per simulation step after the late script updates (`engine/Core/SimulationStep.cpp:RunSimulationStep`), so it only runs in Play and in packaged games, never in the editor viewport.
- `engine/Gfx/EngineFrameRenderer.cpp:EngineFrameRenderer::recordMainPass` particles block — every particle is a `TranslucentDraw` of `builtin://plane` (1.5 m across) whose model matrix spans the view's right and up rows of `m_frameViewMatrix`, rotated by the particle's angle. Each particle gets its own copy of the emitter's material (kept in a `std::deque` so the deferred draws' pointers stay valid) with albedo and opacity scaled by the colour over life, which costs one of the 1024 per-frame material slots per particle; `kMaxParticleDraws` (768) stops before the rest of the frame runs out. An opaque particle material is drawn alpha-blended. A real billboard batch with per-instance colour would remove both limits.
- `engine/Scene/PrefabComponentIO.cpp:CaptureParticleEmitter` / `ApplyParticleEmitter` — the one field list for prefabs, duplication and scene loading (`SceneSerializer.cpp` reads ParticleEmitter through `PrefabComponentIO::ApplyComponentJson`). Scene writing is `SceneSerializer.cpp:WriteParticleEmitterJson`, which must list the same fields; the round trip is covered by `ParticleSimulationTests`.
- `engine/UI/QtEditor/ParticleEmitterInspector.cpp` — numeric fields are driven by one table of member pointers (`NumberField`), so adding a numeric setting means adding one row there plus the capture, apply and scene writer lines.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Weapon.lua:spawnMuzzleSmoke` — the view model is drawn in the camera's frame, so its world muzzle position is not available to scripts; the smoke spawns 0.6 m along the aim ray, offset right and down for the hip pose and under the sight line in ADS.

## Grenades

- `Plugins/HephaestusFPS/Content/Scripts/FPS/Explosives.lua:applyBlast` — damages rows in `Registry.health`, testing each target at its world position (`t:GetWorldPosition`, `engine/Scripting/LuaScriptEngine.cpp:Lua_TransformObj_GetWorldPosition`) lifted 1 m for the player and 0.5 m for everything else, because origins sit at the feet and a ray to the feet grazes the floor. A target is in cover when the ray from the blast hits something else more than 0.25 m short of it; hits on the target or its hit zones count as exposed. The ray skips the calling script's own entity, which is the grenade. Covered by `engine/Tests/FPSLogicTests.cpp`.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Grenade.lua:onUpdate` — `Scene.instantiate` cannot set velocity, so the thrower passes `vx`, `vy`, `vz` as `vars` and the grenade applies them on its first update that has a body.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Player.lua:updateThrow` — the throw reuses the weapon swap's lowering input (`lowering`, `lowerProgress`) with a `sin(pi * t)` dip, so the weapon needs no grenade-specific code; fire and ADS are blocked the same way as during a swap.
- FPS-Shooter grenade prefabs use box colliders. Jolt has no rolling resistance, and angular damping alone did not stop a sphere grenade: at 4.0 it still covered about 6 m between 1.35 s and 2.35 s after the throw.
- `engine/Physics/JoltPhysicsSystem.cpp` Cylinder shape — unlike boxes (`MakeBoxSettings`), cylinders use Jolt's default 0.05 m convex radius, which Jolt rejects for cylinders thinner than that, so small cylinders such as a smoke canister cannot use one.

## Runtime-spawned meshes

- `engine/Scripting/LuaScriptEngine.cpp:LuaScriptEngine::ExecuteSpawn` — a spawned renderer first reuses the handle of any entity with the same `meshAssetPath`; otherwise it calls the host's `SpawnedMeshLoader` (`SetSpawnedMeshLoader`). Before this, a prefab whose mesh no scene entity used stayed invisible.
- `engine/UI/QtEditor/QtEditorEngine.cpp:QtEditorEngine::loadRendererMesh` — the per-entity body of `RebuildSceneMeshes`, lifted out unchanged so the spawn hook uses the same lookup, load and upload. `m_meshFileResolver` is the file resolver `RebuildSceneMeshes` builds for the loaded scene's project; it keeps the roots by value so it stays valid in Play.
- `engine/Game/GameMain.cpp` `loadRendererMesh` lambda — the per-entity body of the packaged game's scene mesh loop, lifted out the same way; it returns whether a mesh was assigned so the loop's loaded count is unchanged. Only the editor side was exercised in Play; the packaged path compiles but was not run with a spawned new mesh.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/ThrowPreview.lua:predict` — integrates like Jolt does for a body (velocity += gravity, then velocity *= 1 - damping * dt, then position) at 1/60 s with a raycast per step, so it matches the real first contact (4 cm off at about 12 m in Editor Play). Gravity is the engine's fixed -9.81 (`engine/Physics/JoltPhysicsEngine.cpp`); damping comes from the player's `throwPreviewDamping` because the player cannot read the grenade prefab's Rigid Body. At a contact the normal velocity is reflected times restitution and the sliding velocity loses friction * (1 + restitution) * normal speed, the size of a Coulomb contact impulse; resting contact falls out of the same rule as gravity pushes into the ground each step. Jolt combines friction as sqrt(a * b) and restitution as max(a, b), so the defaults 0.55 and 0.2 are the grenade (1.0, 0.2) on ground (0.3, 0). Measured over four Editor Play throws: first contact within 0.3 m, second bounce within 0.5 m, end marker within 1.1 m of where the frag was at its fuse; the box grenades tumble with a random spin, which a point model cannot follow. Covered by `engine/Tests/FPSLogicTests.cpp`.
- `engine/Tests/FPSLogicTests.cpp` — the Lua checks are split into adjacent raw string literals because MSVC rejects a single literal over about 16 KB (C2026).
- `ThrowPreview.lua:show` — dot and marker entities are spawned once per aim and moved each frame through `t:SetPosition` / `t:SetRotation` (radians); they are destroyed on release or cancel. The module keeps them in upvalues, which survive between Editor Play sessions because required modules stay loaded, so `Player.lua:onAwake` calls `ThrowPreview.reset()`.

## Character jump timing

- `engine/Physics/CharacterControllerMath.cpp:StepJumpGate` — runs once per controller step before `IntegrateCharacterVelocity`. A jump request is held for `jumpBufferTime` (plus a tiny epsilon, so 0 still means this step only); a character can jump on `OnGround`, or within `coyoteTime` of last being on ground if it has not jumped since. Steep ground does not count as ground. A coyote jump sets `VelocityStepInput::coyoteJump`, and the air branch of `IntegrateCharacterVelocity` then replaces the vertical speed with the jump speed. With both times 0 the behaviour is the old one (covered by `engine/Tests/CharacterControllerMathTests.cpp` and the Jolt walk-off and landing cases in `engine/Tests/CharacterControllerJoltTests.cpp`).
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Logic.lua:directionSpeedScale` — 1 forward, the strafe scale sideways and the back scale backwards, blended by the squared cosine of the input angle. `Player.lua:onUpdate` multiplies it with the ADS move scale, crouch scale and `landingSpeedScale` into `Character.setSpeedMultiplier`; sprint replaces the whole product.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Player.lua:onUpdate` slide — the slide drives the controller through the same calls as walking: `Character.move` with the slide heading and `Character.setSpeedMultiplier` from `Logic.slideSpeedScale`, relative to the controller's walk speed, so the controller's acceleration still smooths the start and the slow-down. A slide starts from the previous frame's `sprinting`, so firing or aiming on the same frame as the crouch press does not start one. The sprint-to-fire delay that ends a sprint is what keeps the weapon from firing in the first part of a slide.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Mantle.lua:find` — rays from the player's axis at 0.3, 0.75 and 1.25 m find a near-vertical wall within the reach; a ray down from above the reach just inside the face finds the top (a hit within 5 cm of the ray start means the ray began inside something taller). A ray at top + 0.25 m along the path must be clear, a vault also needs lower ground 0.9 m past the face, and a mantle needs `standHeight` of clear space above the spot it ends on. `Mantle.position` moves along the path's legs: straight up in front of the face first, so the capsule never overlaps the obstacle, then over. `Player.lua:onUpdate` teleports the character along it each frame (`Character.teleport` zeroes the controller's velocity and refreshes its contacts), which is why the run speed after a vault is rebuilt by the controller's acceleration. Covered by a box-and-ground ray model in `engine/Tests/FPSLogicTests.cpp`.

## Automation runtimes

- `engine/Build/RuntimeLocator.cpp:RuntimeBuildDirectory` — `CMakeRuntimeBuilder::build` configures automation-enabled runtimes in `<engine>/build-automation` and everything else in `<engine>/build`, and `RuntimeLocator::locate` looks in `build-automation/<config>` first only when automation is requested. Before, the builder reconfigured the shared `build` tree with `HEPHAESTUS_RUNTIME_AUTOMATION=ON` and `engine/Build/BuildService.cpp:BuildService::execute` rebuilt it with the option off after packaging; any return before that (cancel, missing runtime) left the option on for the next ordinary build. Covered by `engine/Tests/RuntimeLocatorTests.cpp` and `engine/Tests/BuildServiceTests.cpp` (one runtime build per automation package). The Steam script already uses its own tree (`tools/create_release_package.ps1`).
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Player.lua:onUpdate` tactical sprint — sprinting needs Sprint held, so a double tap ends the sprint for a frame; `sinceSprintEnded` lets a Sprint press within 0.3 s of a sprint ending count as the second tap. `Logic.stepTacticalSprint` spends and refills the charge. `Weapon.lua:tick` picks `tacticalSprintToFireSeconds` for the fire block while `input.tacticalSprint` is set, and `updatePose` blends the barrel-up carry with `row.tacticalBlend`.
- `engine/Physics/CharacterControllerSystem.cpp:CharacterControllerSystem::FixedStep` stances — standing, crouched and prone are ordered 0, 1, 2 by capsule height; the requested stance is prone if `SetProne` asked for it, else crouched if `SetCrouched` did. Switching to a shorter capsule always succeeds; a taller one is tried with `SetShape` and, when it does not fit, the character keeps its stance and reports `standBlocked`. `ClampControllerAuthored` keeps `proneHeight` between the capsule's two end caps and `crouchedHeight`. Covered by the overhang case in `engine/Tests/CharacterControllerJoltTests.cpp`.

## Camera roll

- `engine/Scene/ActiveCameraSync.cpp:MakeCameraViewFrame` — rolls the level right and up axes about the view forward; negative roll tilts the view's up towards its right. `engine/Gfx/EngineFrameRenderer.cpp` builds the main view with `Mat4::LookAt` using that up and uses the same frame for First-Person View Model meshes, so a weapon stays fixed on screen as the view rolls. With roll 0 the view still uses world up, as before. Roll travels `ActiveCameraView::rollRadians` → `PlayModeManager::ApplyRuntimeCameraToRender` (editor) or `GameMain.cpp:ApplyActiveCameraView` (packaged) → `RenderCamera::rollDeg`. Before this the renderer dropped roll, so the FPS slide tilt did not show.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Player.lua:onLateUpdate` lean — the camera is a child of the player, which turns with yaw, so the lean is the camera's local +z (the player's right). The aim origin gets the same world offset, so shots leave from the leaned head. `Logic.leanOffset` limits the offset with a ray from the head towards that side (0.2 m short of a hit).
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Ballistics.lua:step` — semi-implicit Euler at the frame's dt with one ray per bullet per frame along the covered segment; a hit's distance is reported along the whole flight for falloff. `Weapon.lua:fireShot` steps a new bullet once immediately (the first 10 m at 600 m/s and 60 fps), and `Weapon.lua:onUpdate` steps the rest, because the player only calls `tick` on the equipped weapon and bullets must keep flying after a swap. Covered by `engine/Tests/FPSLogicTests.cpp`.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Weapon.lua:spawnCasing` — like the muzzle smoke, the view model is drawn in the camera's frame, so the ejection point is placed from the aim ray (0.3 m ahead, to the right and below, closer in ADS). The player's velocity is passed in `Registry.player.input` (`vx`, `vy`, `vz`) so casings do not lag behind a moving player. `Scene.instantiate` cannot set velocity, so `Casing.lua` applies the `vars` on its first update with a body, as `Grenade.lua` does.

## Normal maps

- `shaders/triangle.frag:perturbNormal` — vertices have no tangents (`engine/Gfx/Vertex.h`), so the tangent frame is the cotangent frame from screen-space derivatives of world position and UV, scaled by the larger axis so it stays invariant to UV scale. A degenerate frame (no UV change across the pixel) keeps the geometric normal. Before this the map was unpacked and mixed 70% into the normal as if it were world space.

## Navigation and enemy AI

- `engine/Navigation/NavMesh.cpp:CollectSceneGeometry` — takes static, non-trigger Rigid Bodies with a Box Physics Shape only (other shapes are counted in `skippedShapes`); kinematic and dynamic bodies, including enemy hit zones, never enter the navmesh. `NavGeometry::AddBox` winds top faces towards +y so Recast marks them walkable. `NavMesh::Build` is the single-tile Recast pipeline (`NavBuildSettings` defaults: 0.2 m cells, 1.8 m by 0.35 m agent, 0.4 m climb, 45 degrees). `NavMesh::RandomPointAround` retries up to 32 times because Detour's `findRandomPointAroundCircle` can return points outside the circle. Covered by `engine/Tests/NavMeshTests.cpp`.
- `engine/Scripting/LuaScriptEngine.cpp:EnsureNavMesh` — builds lazily on the first `Nav` call of a Play session and logs the result; `OnSimulationStarted` and `OnSimulationStopped` drop it, so moved boxes are picked up next Play or by `Nav.rebuild`.
- `engine/Physics/CharacterControllerSystem.cpp:OwnBodiesFilter` — skips bodies whose entity is the character or parented under it. Without it a character with kinematic hit zone children is pushed by its own zones (the `OwnHitBoxes` case in `engine/Tests/CharacterControllerJoltTests.cpp` drifts 41 m).
- `engine/Scripting/LuaScriptEngine.cpp:ExecuteDestroy` — destroying a prefab child destroys the whole prefab instance, so `Plugins/HephaestusFPS/Content/Scripts/FPS/Enemy.lua:onDeath` keeps the hit zones on the corpse instead of destroying them. `Weapon.lua:applyHit` already ignores hits on a dead owner.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Enemy.lua` — `selfKey` is read in `onAwake` because `GetId` returns nil once the entity is being destroyed. Facing uses the plugin's yaw convention (forward `cos yaw, -sin yaw`, `Logic.yawBasis`); `modelYawOffsetDegrees` turns the model on top of that, 90 for EnemyChar, whose forward is +Z. The player is seen through `Registry.player` (`speed`, `stance`, `eyeHeight`, published by `Player.lua:onUpdate`) and hit through its character's inner body, which `Physics.raycast` reports as the player entity.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/AI/Difficulty.lua:resolve` — recruit values, then the chosen preset, then global overrides, then the enemy's own. Copying whole tables keeps `false` values (a `x ~= nil and x or y` pick would drop them).
- `Plugins/HephaestusFPS/Content/Scripts/FPS/AI/Tactics.lua:throwVelocity` — starts from the drag-free ballistic speed for the angle, then simulates the flight the way Jolt integrates a body (gravity, then linear damping, then position, 60 Hz) and scales the speed by sqrt(target / reached) up to six times; the closed-form damping correction missed by more than 0.6 m at 17 m. Covered by `engine/Tests/FPSLogicTests.cpp`.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Grenade.lua:onUpdate` — a frag registers as a danger only below 4 m/s; registered from the hand, it sent the thrower and its allies running on every throw.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/Enemy.lua` combat — the search decision waits a second after entering, because a flanker arrives facing its path and would otherwise give up before turning to look.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/HeldWeapon.lua:onLateUpdate` — aims +X from the grip socket at the support socket with rotation (0, yaw, pitch), which is right for the engine's Rx * Ry * Rz order (`engine/Scene/Components.h:TransformComponent::GetLocalMatrix`); sockets are zero-offset hand bones, so no bone-axis offsets are needed.
- `Plugins/HephaestusFPS/Content/Scripts/FPS/AI/Cover.lua:find` — a spot counts as cover when rays from 1.0 m and eye height to the threat's eye are both blocked, because EnemyChar has no crouch animation. Covered with the other AI modules in `engine/Tests/FPSLogicTests.cpp` (`kAIChecks`).

## Script variables in hand-written assets

- `engine/Scripting/LuaScriptVariableReconciler.cpp:OnScriptSourceChanged` — a value in a LuaScript's `variables` survives the editor's reconcile (run when the Inspector shows the script, and by the `script.reload` tool) only if its name is in `authoredVariables`; unlisted values are reset to the `Expose` default, and on a prefab instance the reset values then differ from the prefab and are saved as per-instance overrides. Only a component with no `authoredVariables` key at all is migrated by treating every existing value as authored. Assets written by tools or scripts must therefore list every value they set in `authoredVariables`. FPS-Shooter lost its weapon definitions and player sounds this way when generated prefabs had values but `"authoredVariables": []`.
